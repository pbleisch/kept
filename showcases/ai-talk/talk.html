  • an append-only record of events in the kept lifecycle
  • stored as a commit graph that lives on its own ref
  • kept operates on it but nobody checks it out
  • reading from and writing to it are intentional
  • does not litter your repo's git log

# 0011 — Everything tracked must merge, because instances are concurrent

## Context

Earlier decisions assumed a single operator and treated concurrency as a problem for later. That conflates two questions. There is one principal — one person who ratifies and lands — but there will be many concurrent writers: several instances of `kept` ticking, repairing, and recording at once.

## Decision

Every format tracked in git must merge without a human resolving it, except where the conflict is genuinely semantic.

The way to get that is to ensure no two writers ever write the same bytes:

1. One file per artifact. …
2. One file per artifact's truth. …
3. Streams are append-only JSONL under `merge=union` …

worked example · the 💩 from the ledger slide

from 460 MB of receipts to a promise worth ratifying

Nothing was measuring it. It turned up by reading the ledger on 2026-10-03.

134,450ledger commits, 124,660 of them in threads/
461 MiBof the 562 MiB pack is receipts
8repair & assessment sessions wrote nearly all of it, in 5 days
7 minto fetch it once, about an hour of CPU

The model's own records (acts, truth, observations) stay under 1 MiB packed. The bloat is all session diagnostics.

why: every line rewrites the whole receipt

One receipt line → one ledger commit → a new blob of everything so far.

each bar is one version of the receipt · bright = stored whole, dim = stored as a delta

Git deltas most versions (median 236 B), but caps chain depth, so every so often it stores a whole copy, each one larger than the last: 378 of the 461 MiB.
The 44,889-line receipt is 34 MB in the tree and 176 MiB in history.

$ kept want "a thread receipt costs the ledger about what it holds"
wrote docs/desire/a-thread-receipt-costs-the-ledger-about-what-it-holds.md

a desire promises nothing

  • no standing, never in a packet: just a place to park the want
  • its state is derived: raw → shaped → committed
  • it carries the evidence (shaped_from) and what would make it writable (ripe_when)

what it must not cost

  • a killed session keeps what arrived before the kill (0052, 0084)
  • the receipt stays in the ledger, and stays content: it is irreproducible
  • no history rewrite: the 461 MiB stays, only future sessions change

directions, not decisions

  • batch lines per commit
  • seal the receipt into segments
  • move native events out as content-addressed payloads

Shaping = a becomes and a candidate that would load. The hard part is what number the promise holds.

Bound the packed bytes?
No. Packing is git's choice of deltas and chain depth. A promise on it measures git, not kept.
Then what can kept count?
What each write introduces: blob + trees + commit. Cap that and the total is linear, whatever git packs.
A clause for commit count?
Not needed. Commit overhead is inside the per-write number. It's 7.5% today, and it becomes the floor once the blobs are fixed.
Can the repair agent pick A and c?
No. The bound is what is owed, and only a person's ratification gives it standing. An agent works toward a predicate and never authors it.
candidate clause each ledger write for a receipt introduces ≤ A × bytes it adds + c · plus a kill test for durability

why this needs an ADR before code

  • Store.Append promises one line, durable before it returns (0016, 0018). Batching or a journal changes that seam.
  • Segments change the layout of ledger/threads/, and every reader that folds a receipt.
  • 0084 put a spool in front of the receipt and left this open: "batching stays open if a receipt's size or latency forces it." Now it has.
  • The ADR chooses with a measurement: replay a recorded receipt through each design into a scratch ledger.

  1. Answer the loss bound: zero lines, or at most B lines?
  2. Shape it: becomes: promise plus a candidate with two clauses. Desire → shaped.
  3. Write the tests first: replay + kill. Watch today's code fail them. A check that never fired is not a check.
  4. Write the ADR: the replay picks the layout.
  5. Build it, run kept shape --trial, break it on purpose, then kept ratify. Desire → committed.
  6. Then tighten A and c to the measured numbers plus margin, if efficiency, not just linearity, should be held.
